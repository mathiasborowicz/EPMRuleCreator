# Microsoft Graph and EPM rule model

## Current implementation

The optional Graph connection lists Endpoint Privilege Management Elevation Rules policies, reads rule counts and reusable certificate settings, and can add or update a rule or create a policy with its first rule when the user clicks the upload button. It also lists, creates, reads, and updates Elevation System Settings policies. Policy writes happen without an additional confirmation dialog.

The app lists policies with `GET /beta/deviceManagement/configurationPolicies`, filtered by `templateReference/templateFamily eq 'endpointSecurityEndpointPrivilegeManagement'`, selecting the metadata shown in the UI. It follows `@odata.nextLink`. For the selected policy it reads `GET /beta/deviceManagement/configurationPolicies('{id}')/settings?$expand=settingDefinitions&$top=1000`, also following `@odata.nextLink`.

The test-tenant response supplied for this implementation confirms the root setting instance type `deviceManagementConfigurationGroupSettingCollectionInstance` and definition ID `device_vendor_msft_policy_privilegemanagement_elevationrules_{elevationrulename}`. Rules are counted from the root instance's `groupSettingCollectionValue`; the supplied response contained two entries. Its expanded definition reported `maximumCount: 100` and `minimumCount: 1`. Policy-level `settingCount` is not the number of elevation rules.

The app requests the setting definition's `maximumCount` when available and otherwise uses the observed EPM limit of 100. A policy with existing settings but no identifiable EPM root collection is treated as an error rather than guessed to be empty.

Reusable settings are listed through `GET /beta/deviceManagement/reusablePolicySettings`. This collection also contains unrelated Intune settings, so the app filters client-side by the exact EPM certificate definition ID `device_vendor_msft_policy_privilegemanagement_reusablesettings_certificatefile`. The test tenant returned the EPM setting "Netextender" and an unrelated Defender setting; only the former should appear in the EPM certificate selector. Results are paged using `@odata.nextLink`.

For **Signature source**, the app supports **Not configured**, **Upload a certificate file**, and **Use a certificate file in reusable settings**. An uploaded certificate can come from the analyzed file's signing certificate or a selected `.cer`, `.crt`, `.pem`, or `.der` file. Extraction does not validate Authenticode trust. **Certificate type** supports the observed values `publisher` and `issuingauthority`. For writes, the app refreshes the policy and all settings, clones an existing rule with the matching signature-source/elevation-type shape, changes the selected values, and sends a `PUT` to the policy resource with the policy fields and complete settings collection. The setting objects are serialized as `@odata.type` plus `settingInstance`, matching the request observed in the Intune admin center browser. This preserves the other settings and existing rules. After upload, it rereads the policy and checks the count. If Graph rejects the write or verification fails, the UI reports the result; after a verification failure users should check Intune before retrying.

Important API discrepancy: Microsoft Graph's published beta documentation currently specifies `PATCH /deviceManagement/configurationPolicies/{policyId}/settings/{settingId}` for an individual setting and `PATCH /deviceManagement/configurationPolicies/{policyId}` for a policy. In the user's test tenant, the documented setting PATCH returns a routing error; the request captured from the Intune admin center instead uses `PUT /deviceManagement/configurationPolicies('{policyId}')` with a full policy body. The app follows that observed request, but the PUT behavior is not listed in the public update documentation and remains subject to live validation in the user's tenant.

For existing Elevation Rules policies, the app reads the existing collection, prefills an existing rule selected for editing, and detects duplicate names, hashes, and file versions. It also surfaces rules using the same signing certificate as context. If an incoming rule matches existing rules, the user can update a selected match or add another rule. Before writing, the policy and settings are reread; the update replaces the selected rule while preserving the other rules, and the append path preserves the full collection. Appending requires an existing EPM root setting and at least one existing rule to serve as a base payload template; the requested **Elevation type** does not need to exist already. The app rebuilds type-specific validation children from the selected type. **Restrict Arguments** supports **Not configured** and **Allow**; each argument is a string setting value. Empty optional text settings and unselected optional validation collections are omitted. The supplied file-version definition accepts exactly four numeric components when set; analyzed versions are normalized to four components. Appended rules omit instance/value template references to avoid duplicating references already attached to the original rule. The 100-rule limit and current settings are reread immediately before PUT, but concurrent edits after that read cannot be excluded.

## Elevation System Settings policies

The app lists policies using the Elevation System Settings template ID `598096f6-4121-4088-859f-b11ebfbd09bc_1`. Selecting a policy reads its configuration and prefills the editor. The supported setting is **Allow standard users to change network settings**, with **User confirmed** or **Automatic** elevation. User-confirmed mode can require Business justification, Windows authentication, both, or neither. Automatic mode does not expose validation options. The editor can also create a new policy. Updates reread the policy and complete settings collection, preserve unrelated settings, send the updated policy, and verify the values by reading them back. New policies use Windows 10, Endpoint Privilege Management, scope tag `0`, and no assignments.

## Creating a policy with its first rule

The policy dropdown always includes **+ Add new**, including for an empty tenant. This opens a required policy name and optional description in the rule editor. It creates a local draft only. **Create policy and upload rule** validates the rule against a zero-rule target, logs progress, and sends one `POST /beta/deviceManagement/configurationPolicies` containing the policy and initial settings. No empty-policy POST or following append is attempted.

The POST route, response (`201 Created`), permission (`DeviceManagementConfiguration.ReadWrite.All`), Windows platform and EPM technology are documented by Microsoft. The policy resource exposes its `settings` relationship. The EPM template ID `cff02aad-51b1-498d-83ad-81161a393f56_1` and root setting instance template ID `ee3d2e5f-6b3d-4cb1-af9b-37b02d3dbae2` come from the supplied Intune admin-center payload. These are schema identifiers, not tenant or application IDs. The initial rule is built from the form values and known EPM setting definitions, without an existing rule. Only the root instance gets its template reference; rule values do not duplicate template references. The request supplies only `templateReference.templateId`, since Microsoft's template-reference resource marks the family/display metadata read-only.

The policy uses `windows10`, `endpointPrivilegeManagement`, the default scope tag `0`, and no assignments. After creation, the returned policy ID is selected and the app reads the settings back to check for one rule. An interrupted response is not automatically retried. If creation succeeds but verification fails, the UI retains the created policy and its ID so the user can inspect it instead of creating another copy.

On 2026-10-22, the user confirmed that creating a new policy together with its first rule succeeds in the test tenant. The POST path also has local payload and mocked HTTP tests covering all five elevation types and three certificate-source modes. The live confirmation applies to the user's tested scenario; it does not establish live acceptance for every combination or for a completely empty tenant. When hash identification is selected (`signaturesource` not configured), file name and SHA256 hash are required. When a publisher or reusable certificate is selected, those two fields are optional; if left blank, their setting instances are removed from the rule payload rather than serialized with empty values. The optional minimum file version is also omitted when blank.

## Permissions

The app requests delegated `User.Read` (signed-in identity) and `DeviceManagementConfiguration.ReadWrite.All` (policy/settings reads, policy creation and updates). Admin consent is required. The policy create and setting create/update beta API documentation identify this permission; `DeviceManagementEndpointSecurity.ReadWrite.All` is not additionally required for these endpoints.

- [Create a configuration-policy setting](https://learn.microsoft.com/en-us/graph/api/intune-deviceconfigv2-devicemanagementconfigurationsetting-create?view=graph-rest-beta)
- [Update a configuration-policy setting](https://learn.microsoft.com/en-us/graph/api/intune-deviceconfigv2-devicemanagementconfigurationsetting-update?view=graph-rest-beta)
- [Permission reference](https://learn.microsoft.com/en-us/graph/permissions-reference#devicemanagementconfigurationreadwriteall)
- [List reusable policy settings](https://learn.microsoft.com/en-us/graph/api/intune-deviceconfigv2-devicemanagementreusablepolicysetting-list?view=graph-rest-beta)
- [Reusable policy setting resource](https://learn.microsoft.com/en-us/graph/api/resources/intune-deviceconfigv2-devicemanagementreusablepolicysetting?view=graph-rest-beta)

Graph consent does not replace Intune licensing or the signed-in user's Intune RBAC role and scope-tag access.

## Validation notes and limits

Automated Graph HTTP tests use mocks. The user has confirmed policy creation and system-settings policy creation/update in a test tenant. Confirm server-side behavior for simultaneous admin edits; no concurrency token was included in the supplied payload. Graph beta behavior and acceptance of less common setting combinations can change and should be checked in the target tenant.
